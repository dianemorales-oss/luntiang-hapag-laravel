# Repo cleanup — duplicate files and size

## What was wrong

The working tree was **366 MB** across **9,307 files**. Two separate causes,
often confused for each other:

### 1. File count — `vendor/` (not a problem)

8,569 of the 9,307 files were `vendor/` — Composer's third-party libraries
(`laravel/framework` 1,742 files, `phpunit` 975, `carbon` 928, ...). It is
already gitignored (`.gitignore` line 8), never committed, and regenerated by
`composer update`. This is normal for every Laravel project and was left alone.

Git only ever tracked **684 files**.

### 2. Disk size — duplicated asset trees (the real problem)

Images totalled **214 MB** on disk but only **63 MB** of unique content.
Roughly **150 MB was redundant copies**. Some files existed **8 times**.

The main culprit: a **complete stale copy of the project had been committed
inside `storage/`** — `storage/public/`, `storage/original/`,
`storage/resources/`, `storage/database/`, even `storage/artisan` and
`storage/composer.lock`.

That copy was verified to be an **older, pre-offline-fix snapshot**:

- `storage/resources/views/admin/layouts/app.blade.php` still used
  `https://cdn.tailwindcss.com` and Google Fonts, where the real file uses
  `@include('partials.offline-assets')`.
- `storage/composer.json` had **no** `config.platform.php` pin, where the real
  one pins PHP 8.2.0 for WAMP.

So it was strictly stale — keeping it risked someone editing the wrong file.

## What was removed

| Path | Before | After | Notes |
| --- | --- | --- | --- |
| `storage/` | 87 M | 269 K | stray project copy deleted; real `app/`, `framework/`, `logs/` kept |
| `original/` | 35 M | 941 K | 40 duplicate images removed; **code kept** |
| `uploads/` | 31 M | 85 K | 16 byte-identical dupes removed; `image.png` kept |

**Total: 366 MB → 217 MB.** Tracked files: 684 → 358.

## What was deliberately kept

- **`vendor/`** — normal, gitignored, regenerated by `composer update`.
- **`original/includes/`** — *still used by running code*:
  - `app/Helpers/LettuceCatalog.php` → `original/includes/lettuce-catalog.php`
  - `app/Services/ChatbotEngine.php` → `original/includes/chatbot-knowledge.php`
- **`original/uploads/.htaccess`** — the only non-duplicate file there.
- **`uploads/image.png`** — the only file with no counterpart in `public/`.
- **`public/images/`** — the canonical copy the app actually serves.
- **`composer.json` / `composer.lock`** — untouched, so the PHP 8.2 platform
  pin and Symfony 7.4 lock still work on WAMP.

## Safety checks performed

Every deletion was verified byte-for-byte with `cmp` against its canonical
counterpart before removal. Checks run:

- `grep` for `storage/public`, `storage/original`, `storage_path('public')` in
  `app/`, `resources/`, `routes/`, `config/` → **no references**.
- Root `uploads/` → all app code references `public/uploads` via
  `public_path()`, never the root folder.
- `original/images` + `original/uploads` → 40 duplicates, 0 unique (except
  `.htaccess`).

## Verification after cleanup

- `php artisan migrate` — all migrations pass.
- `php artisan test` — **6 passed**, including the 4 CSRF/419 regression tests.
- Pages returning `200`: `/`, `/products`, `/cart`, `/faq`, `/login`,
  `/contact-support`.
- `LettuceCatalog::get()` → 19 items OK (reads `original/includes/`).
- `ChatbotEngine::greeting()` → OK (reads `original/includes/`).
- Product images still serve `200`:
  `images/lettuce/5-bianca-lettuce.jpg`, `images/lettuce/50-red-lettuce.png`.
- The 419 fix still works: stale token → friendly redirect; valid restore →
  Customers page with success banner.

## Still outstanding: `.git/` is 65 MB

Deleting files now does **not** shrink history — the large images are still in
past commits. Reclaiming that requires rewriting history
(`git filter-repo` / the repo's own `FIXES/clean-history.sh`) followed by a
**force-push**, which rewrites every collaborator's clone. Not done here
because it is destructive and should be a deliberate decision.

Separately, the source images are unoptimised — a 6 MB PNG of a lettuce photo
would be roughly 200 KB as WebP. Converting them would cut `public/` (still
69 MB) by an order of magnitude.
